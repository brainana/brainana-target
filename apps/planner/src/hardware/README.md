# Electrode hardware catalog and geometry

The catalog is a reviewed, offline snapshot of manufacturer pages and primary papers, checked 2026-10-11. Each entry carries source URLs, published facts and explicit illustrative assumptions. This is a planning library, not a product ordering configurator or exact manufacturer CAD library. No websites are fetched when loading a user's project.

## Adding a preset

Add a `HardwarePreset` in `catalog.ts`, with mm dimensions, facts, assumptions and direct primary-source links. Verify the precise device variant. Use `geometry` to define a round shaft or rectangular blade, regular array rows / columns / pitch, site columns / pitch, first site centre offset, and simultaneous recording channel count. `sites` is physical sites per shaft, not recording channels. `length` initializes a template; `configuration.ts` then applies family-specific defaults, including reinforcement reserve for U-Probes. Selecting a preset opens an isolated, validated configuration draft. Cancel leaves the project untouched; Apply commits all device changes as one undoable transaction and preserves its target link. FMA requires an explicit physical-electrode variant choice. Numbered electrode-length fields match the live footprint preview. Acquisition-system selections are metadata and do not change targeting. Reset to preset dimensions restores the chosen template after customization. Selecting a preset copies its full definition into the project, so future catalog updates do not change saved plans.

Run `npm run planner:test`, `npm run planner:build`, and `npm run lint`. `hardware_test.mjs` validates every catalog entry and checks array targeting, different shaft lengths, exclusions, blade envelopes, coordinate exports and portable round trips. `configurator-smoke.mjs` exercises the current configuration window, all 14 sourced defaults, explicit FMA variants, Cancel, numbered electrode lengths, save and one-step Undo/Redo. `large-project-smoke.mjs` tests feasible placement and numerical short-FMA reach diagnostics on the example monkey.

## Geometry and placement

`packages/planning-core/hardware.ts` generates local shaft offsets and site coordinates independently of UI and renderer. The existing `Electrode` remains a placed device. Its optional `hardware` definition describes a regular rigid assembly whose centre is anchored at `hole`. Local X/Y offsets rotate with `hardware.rotation` and the chamber. The target reference is the tip of `selectedShank`, never a virtual tip between shafts. `depth` is its insertion from the grid plane. Different shaft lengths share a fixed proximal plane, so other insertion depths change by the length differences. `reservedLength` is a common portion held above the grid; usable + reserved gives the physical shaft length.

`electrodePaths` gives every shaft; `trajectory` returns the selected reference path for the existing trajectory views and guide. The search tests every inserted shaft against exclusion capsules, and conservatively tests the whole footprint against the chamber bore. Rectangular blades use an enclosing circular cross-section for clearance. New-chamber search offsets the assembly centre so the reference shaft reaches the target while retaining the exterior support-plane constraint. It does not perform a search over device roll; set rotation explicitly before searching.

Legacy devices without `hardware` preserve their existing contact and insertion semantics. Hardware devices allow proximal physical sites above the grid during partial insertion. The site layout must fit the total physical length, not the inserted segment. Full site coordinates are exported, including negative insertion coordinates for uninserted proximal sites. Planning IDs are independent of manufacturer channel wiring.

## Display and performance

The 3D scene uses actual shaft diameter or blade width / thickness. White overview site markers are enlarged and sampled to at most 512 per device; exported geometry retains every site. The side / footprint inspection window lets users select a reference shaft and inspect total physical length. Its side widths and site detail are schematic; footprint proportions are physical. Anatomical cross-sections show neighboring shafts near the selected plane.

Constraint calculations omit site generation, so a high-density site's count does not multiply search cost. Hardware definitions participate in search invalidation, undo/redo, autosave and portable project export.

## Current limits and next extensions

Exact manufacturer wiring maps, recording banks, connector / substrate / reinforcement bodies, needle taper, individual grid-hole alignment, guide tubes and inter-device collisions are not modeled. Cortical Utah/FMA arrays are represented geometrically but are not automatically fitted to cortex independently of the chamber grid; a tall chamber usually makes these short needles unreachable. Add a dedicated surface-mounted-array workflow before claiming implantation fit. None of these templates are fabrication-ready models.

Explicit `sitePositions` now support arbitrary sites, grouped patterns and opposing faces. `configuration.ts` keeps option units, dependent constraints and physical model updates outside the UI. `options-panel.ts` renders these sourced options. See [SOURCE-AUDIT.md](./SOURCE-AUDIT.md) for coverage, source conflicts and remaining models. The two manufacturer test files check applied geometry and actual saved browser state.

Future arbitrary-shaft definitions should be normalized by the core geometry module and reuse its full-array constraint checks. Keep manufacturer channel maps separate from physical site positions. Connector / substrate geometry will need explicit collision primitives and holder compatibility, rather than decorative meshes used only in rendering.

The configuration dialog lives in `configuration-dialog.ts`; it receives a field renderer instead of importing feature panels. Its private ProjectStore uses the same project validation as committed edits. `optimization.ts` reports sampled depth requirements and available insertion range without changing hardware; positioning translates these into numerical diagnostics and specific remedies. Failed sampling does not prove every possible pose infeasible. Independent cortex-mounted arrays remain a separate future workflow.

Hardware dropdowns use `availableChoices()` to run candidate selections through the configuration rules without mutating the draft. Dependent accessory, layout, pitch and reinforcement choices therefore update together. `gridCompatibility()` centralizes single-shaft guide availability; rigid multi-needle arrays retain their reference location in fixed-placement searches, and the UI does not advertise a regular guide as an array mount. `ui/hoverHelp.ts` provides hover and keyboard-focus explanations, including aria-disabled workflow controls and controls inside dialogs.

Dependent inputs use `ui/revealField.ts`: mark destinations with a follow-up key and request reveal after the validated edit and redraw. The helper opens collapsed ancestors, scrolls the required input into view, focuses it and briefly highlights its section. Individual profiles lead to per-shank lengths; generated nonuniform patterns lead to their short-end length; optional rigid tubing leads to tube length. Inactive pattern and tubing fields are hidden. Follow-up navigation is triggered by choosing a mode, not by each subsequent numeric edit.

FMA uses the manufacturer terms Uniform, Slanted, Staggered and Clustered. These are configurable length arrangements, not verified factory-default endpoint lengths. Generated layouts are planning examples; confirm the ordered length map. Nonuniform controls expose Shortest electrode length and Longest electrode length. Editing any numbered electrode converts Uniform to Individual lengths while retaining every other length. Common-length edits restore Uniform and synchronize the configuration baseline. Dormant shortest-length values adapt to a shorter common baseline, so valid configuration choices cannot disappear behind a hidden dependent input.

`setup.ts` defines initial geometry prerequisites by family. Configurable families and custom devices cannot show a preview or dependent controls until the user chooses required options and confirms the starting specifications. Choices unlock subsequent inputs in order. Specific fixed Neuropixels models are immediately defined by preset selection; acquisition/connector metadata never blocks their physical preview. A persisted per-preset confirmation preserves applied configurations on reopen; selecting or resetting a preset clears it. Cancel and unfinished setup never change the applied project.
